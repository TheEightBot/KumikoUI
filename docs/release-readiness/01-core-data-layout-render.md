# KumikoUI 1.0 readiness review — Core data, layout and rendering pipeline

Scope: `src/KumikoUI.Core/Models/*`, `Layout/GridLayoutEngine.cs`, `DataGridRenderer.cs`, `Rendering/*`, compared against `README.md`, `.github/instructions/*.md` and `tests/KumikoUI.Core.Tests`.
Reviewed at `main` (59825e2). PR #9 (`feature/uno-platform-port`) changes only two files in this slice: `DataGridRenderer.cs:238-281` and `Models/GridState.cs:231-236` (`PinBottomSummaryRows`); those are covered in CORE-09. All other line numbers refer to `main` and are identical on the PR branch. No repo files were modified.

## (a) Summary

- **Crash-level gaps on non-happy inputs.** Sorting any column whose values are not mutually `IComparable` (Template/action columns with empty `PropertyName`, mixed `int`/`double`, custom classes) throws on a plain header tap because `AllowSorting` defaults to true (CORE-01). Null items, heterogeneous item types and a stale `CurrentCell` after filtering also throw (CORE-06, 14, 15).
- **Documented behaviour diverges from code.** The README's own table-summary XAML silently drops the `Sum` because computed values are keyed by property name (CORE-02); `ColumnSizeMode.Auto` never auto-measures (CORE-07); `Width="*"` cannot be parsed; "multi-sort via code" produces a single sort; and the Copilot instructions/prompts describe an API (`BeginUpdate/EndUpdate`, `ApplySort`, `ApplyFilter`, `FilterLogicalOperator`, public `RebuildView`) that does not exist (CORE-11, 38).
- **Performance claims hold for row virtualization, not per-cell work.** Every visible cell per frame allocates an accessor-cache key string, boxes the value, formats a display string and allocates a `GridPaint`; text is re-measured/ellipsised every frame; `PaintCache` is rebuilt every frame; summary and INPC paths trigger full O(n log n) rebuilds with no batching; INPC tracking allocates a `WeakReference` (GC handle) per item and untracks in O(n) (CORE-10, 19, 20, 21, 22, 34).
- **No thread-affinity contract.** `INotifyCollectionChanged`/`INotifyPropertyChanged` handlers rebuild `_viewIndices`/`_flatView` on the raising thread while the UI thread renders from them; hosts marshal only the repaint (CORE-05).
- **API hygiene is not 1.0-ready; most fixes are breaking.** Runtime state (`Width`, `SortDirection`, `ActiveFilter`) is publicly mutable on `DataGridColumn` with no notification; `SelectionModel` exposes mutable `HashSet`s and index-only selection; `DataChanged` is an argument-less `Action`; events are raised inconsistently; dead properties (`RowStyle.Height`, `CellStyle.Border*`, `Column.Id`, `SelectionUnit.Cell`) exist; ~55 public members lack XML docs; there is no `Dispose`. PR #9's pinned footer (default on) also regresses hit-testing and keyboard scrolling (CORE-09).

## (c) Questions for the maintainer

1. **Threading contract (CORE-05):** Is `DataGridSource` meant to be UI-thread-only (document + assert), or should it capture a `SynchronizationContext` in `SetItems` and marshal INCC/INPC rebuilds itself? The MAUI host currently assumes the former but only half-enforces it.
2. **Selection identity (CORE-06):** After sort/filter/collection changes, should selection follow the *items* (survive reorder) or be cleared? Which event should hosts rely on to reconcile?
3. **`SelectionUnit.Cell` (CORE-26):** In scope for 1.0, or should the enum value be removed before the API freezes?
4. **`ColumnSizeMode.Auto` (CORE-07/24):** Auto-measure on load (what sample size for 100K rows?) or redefine Auto as "double-click to fit" and fix the README?
5. **Comparison semantics (CORE-13):** Should row sorting be culture-sensitive (current) or ordinal; case-sensitive or not; and should group ordering follow the raw key/`CustomComparer` rather than display text?
6. **Column/selection mutability (CORE-27/28):** Are you willing to make the breaking change to read-only runtime state (`Width`, `SortDirection`, `SortOrder`, `ActiveFilter`, `SelectedRows`) before 1.0, given it cannot be done after?
7. **Summaries (CORE-02):** Should a column be able to show several aggregates (stacked, joined) or should the model reject duplicates? The README example implies the former.
8. **Dead properties (CORE-30):** `RowStyle.Height` and `CellStyle.BorderColor/BorderWidth` — implement variable row heights/cell borders, or delete?
9. **PR #9 default (CORE-09):** Is `PinBottomSummaryRows = true` an intentional behaviour change for existing users, and should the PR be blocked until hit-testing/ensure-visible are updated?
10. **Localization/RTL (CORE-32):** Are localized built-in strings and RTL in the 1.0 scope?
11. **Nested INPC (CORE-18):** Should the grid observe nested objects (`Address.City`), or is "raise on the root" the documented contract?
12. **Decimal aggregates (CORE-40):** Do target users need exact `decimal` sums (finance), or is `double` acceptable?
13. **Stale instruction docs (CORE-11):** Were `BeginUpdate/EndUpdate`, `ApplySort(s)`, `ApplyFilter` planned features (batching would fix CORE-20) or leftovers from an earlier design? Which is the source of truth, README or `.github/instructions`?
14. **Frozen-row semantics:** Frozen rows are "first N rows of the current view" (`Models/DataGridSource.cs:126-135`), so after a sort different items are frozen. Intended, or should pinning be item-based?
