# KumikoUI 1.0 readiness review — Core components, editing pipeline, input handling

Scope: `src/KumikoUI.Core/Components/*`, `src/KumikoUI.Core/Editing/*`, `src/KumikoUI.Core/Input/*` (all files read in full), cross-checked against `DataGridSource.SetCellValue/GetItem`, `DataGridRenderer` call sites, `SelectionModel`, the MAUI host (`src/KumikoUI.Maui/DataGridView.cs`) where it decides whether a Core feature is reachable, README.md and `.github/instructions/components-and-editing.instructions.md`. All line numbers refer to the worktree at commit `59825e2` (branch `feature/uno-platform-port` differs from this tree only by `tests/KumikoUI.Uno.Tests/*`, so nothing in this slice changes on the PR). The `src/KumikoUI.Uno` host is not present in this checkout and was not reviewed.

## (a) Summary

- **The edit session is never invalidated when the row view changes.** Sorting (header tap), filtering, grouping, collection changes and ObservableCollection updates all happen while an editor is open, and `CommitEdit` writes by stale visible-row index (`EditSession.cs:295-310`), so the value lands on the wrong item or `DataGridSource.GetItem` throws out of the input handler. Nothing in Core or the MAUI host calls `CommitEdit`/`CancelEdit` on any of these transitions.
- **Several editors silently overwrite data.** ComboBox (value not in list / type mismatch → `null`), ScrollPicker (→ item 0), DatePicker (`null` → today, time-of-day truncated, `DateOnly`/`DateTimeOffset` cannot round-trip) and any custom `DrawnComponent` editor (→ `null`) commit a value the user never chose as soon as they tap elsewhere; numeric conversion loses `decimal` precision and `Convert.ChangeType` failures are swallowed while `CellValueChanged`/`CellEndEdit(committed:true)` still fire.
- **Two advertised features are unusable past trivial sizes:** the Excel-style filter popup's value list cannot be scrolled at all (`_isPanning` is never set, wheel is never routed) so only ~10 distinct values are reachable and dragging toggles checkboxes; the ComboBox dropdown cannot be scrolled by pointer and keyboard-only users cannot change a ComboBox value because the grid intercepts Enter before the editor.
- **Keyboard/pointer plumbing has correctness bugs:** keyboard auto-scroll adds `OffsetY` twice and ignores frozen rows/summaries (every call site omits `dataSource`), the editor overlay is never repositioned on scroll (`UpdateEditorBounds` has no callers), Tab is a keyboard trap that ignores `EditTriggers.None`, `AllowRowDragDrop` hijacks vertical touch scrolling, clipboard inside editors is dead (no `PasteRequested`/`CopyRequested` subscribers anywhere; Cut deletes without copying), right-click/long-press have no context-menu surface, and `SelectionUnit.Cell` is unimplemented.
- **No accessibility surface and almost no tests.** Core exposes no semantic tree; the host only labels the whole canvas "Data grid". Of 19 files in this slice only `InertialScroller` has tests; `EditTriggerResolutionTests` tests a local copy of the rule, not `GridInputController`. `EditSession`, `CellEditorFactory`, `GridInputController`, `GridHitTester`, `PopupManager`, `FocusManager` and every `Drawn*` component have zero coverage. README/instructions samples reference members that do not exist (`Min/Max`, `EditTextSelectionMode="End"`, `CellValidationResult.Success`, `ColumnType="ProgressBar"`).

## (c) Questions for the maintainer

1. **Commit vs cancel on view change.** When the source re-sorts/filters/regroups or an `ObservableCollection` change arrives mid-edit, should the pending value be committed to the *item* (tracked by reference) or discarded? Both are defensible; today it is "write to whatever row index is there now".
2. **Is `SelectionUnit.Cell` in scope for 1.0?** It is public API and in the README but has no implementation. Ship it, or remove the enum value and README rows?
3. **Is `DrawnActionButtons` meant to run through `EditSession` at all?** It carries no value; today each tap produces a bogus `CellValueChanged(rowItem → null)` and a `DataChanged` rebuild. A dedicated "interactive cell" path (no edit session) would avoid the stale-row crash after a Delete command.
4. **Full-row drag gesture:** README says long-press, code starts on an 8 px vertical move. Which is intended (long-press is the only touch-friendly option)?
5. **Should an outside tap that dismisses a popup also act on the grid?** Platform convention (and the filter popup's Cancel semantics) suggests swallowing it; `PopupManager` deliberately does not.
6. **Supported editable property types for 1.0:** `enum`, `decimal`, `DateOnly`, `TimeOnly`, `DateTimeOffset`, `Guid`, nullable value types? None of these round-trip today. Also: should empty numeric text mean `null` (nullable) / unchanged (non-nullable) / validation error?
7. **Localization strategy** for drawn strings ("(Blanks)", "Sort A-Z", "OK/Cancel/Clear", calendar day names, AM/PM) — resource-based `GridStrings` on `DataGridStyle`, or host-provided delegate?
8. **Accessibility bar for 1.0:** is screen-reader row/cell navigation required, or is a documented "visual only" limitation acceptable for the first release? (It affects whether A11Y-01 is a release blocker.)
9. **`DrawnCheckBox` / `DrawnProgressBar` / `FocusManager.FocusNext` / `DrawnTextBox.Validation`:** keep as public (and test them) or mark `internal`/remove before the API freezes?
10. **Keyboard model:** should `GridKey` stay a curated enum (A/C/V/X/Z) or become key + modifiers + character so hosts can map Ctrl/Cmd shortcuts generically (needed for COMP-03)?
11. **Should Tab be allowed to leave the grid** (focus the next control) at the last editable cell, and should `EditTriggers=None` columns be skipped by Tab?
