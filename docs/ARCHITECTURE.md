# Architecture Overview

This document describes the architecture of KumikoUI DataGrid (the canvas-drawn DataGrid for .NET MAUI and the Uno Platform, rendered with SkiaSharp) for contributors and maintainers. It describes the code as it is: when it and the code differ, the code wins, and `dotnet run --project eng/DocsIdentifiers -c Release` fails on a type, member or file this document names that no longer exists. For the frame itself see [RENDERING.md](RENDERING.md); for input timings see [INTERACTION.md](INTERACTION.md); for text input and input methods see [TEXT-INPUT.md](TEXT-INPUT.md); for using the Uno host see the [Uno user guide](uno/README.md).

## Dependency Graph

```
KumikoUI.Core (net10.0, no external dependencies)
       ↑
KumikoUI.SkiaSharp (net10.0 → SkiaSharp, SkiaSharp.HarfBuzz)
       ↑                              ↑
KumikoUI.Maui                    KumikoUI.Uno
(net10.0-ios/-android/           (net10.0-desktop/-browserwasm/-ios/-android/
 -maccatalyst/-windows →          -windows → Uno.WinUI + SkiaSharp.Views for Uno)
 MAUI + SkiaSharp.Views.Maui.Controls)

KumikoUI.SourceGenerators (netstandard2.0, Roslyn) ── analyzer inside the KumikoUI.Core package
```

Four packages ship: `KumikoUI.Core` (with the generator), `KumikoUI.SkiaSharp`, `KumikoUI.Maui` and `KumikoUI.Uno`, all at one version. The two hosts never reference each other.

**KumikoUI.Core** has no dependency on any rendering or UI framework. All rendering operations go through the `IDrawingContext` abstraction, making the core portable to any backend (SkiaSharp, Direct2D, CoreGraphics, HTML Canvas, etc.).

## Key Classes

### Core Infrastructure

| Class | Responsibility |
|-------|---------------|
| `KumikoRenderer` | Orchestrates the frame: layout, the pane passes, overlays, editor and popups (`RenderFrame`) |
| `KumikoSource` | Data management: filtering, sorting, grouping, summaries, change observation, display-text cache |
| `KumikoLayoutEngine` | Column width computation (Auto/Star/Fixed, header fit), visible row and column ranges |
| `FrozenPanes`, `PinnedGroupHeaders`, `KumikoScroller` | Which frozen columns stay pinned, sticky group headers, scroll-to-row and column offsets |
| `KumikoHitTester` | Resolves pointer coordinates to one of 13 `HitRegion` values, with the geometry the renderer drew |
| `InteractionGeometry`, `RenderedHitRegions` | Hit and draw sizes both sides share; the regions a frame measured (grouping chips) |
| `PaintCache` | The `KumikoPaint` objects the grid draws with, rebuilt from `KumikoStyle` only when the style changes |
| `ScrollState` | Scroll offsets, viewport and content size, `BottomInset` for the on-screen keyboard |

### Input & Selection

| Class | Responsibility |
|-------|---------------|
| `KumikoInputController` | Routes pointer and keyboard events to selection, editing, sorting, resizing, reordering, drag and popups; raises `NeedsRedraw`, `CursorChanged`, `HapticFeedbackRequested` |
| `KumikoSelectionModel` | Item-based selection, current cell, Single/Multiple/Extended modes, navigation |
| `DrawnFocusManager` (internal) | Single-component focus model with Tab cycling |
| `PopupManager` (internal) | Popup lifecycle, z-order, input priority routing |
| `InertialScroller`, `ScrollSettings` | Physics-based scroll deceleration, normalized by frame time; momentum presets |
| `InteractionAnimations`, `InteractionFeedback` (internal) | Hover and pressed state, row and column pick-up, drop and group-slide transitions |
| `ITextInputSession` | What a text editor offers a host's native text-input object (see TEXT-INPUT.md) |

### Editing

| Class | Responsibility |
|-------|---------------|
| `EditSession` | Cell edit lifecycle: begin, validate, commit, cancel; places and draws the editor |
| `CellEditorFactory` | Creates the appropriate `DrawnComponent` editor for each column type, applies theme and font |
| `EditorDescriptor` | XAML-declarable editor configuration (for example `NumericUpDownEditorDescriptor`) |

### Rendering Abstractions

| Class | Responsibility |
|-------|---------------|
| `IDrawingContext` | Platform-independent API: rectangles, lines, polygons, text, images, clipping |
| `SkiaDrawingContext` | `SKCanvas` implementation; a thin per-frame wrapper handed out by `SkiaResourceCache.CreateContext` |
| `SkiaResourceCache` | Per-control, bounded cache of `SKPaint` / `SKFont` / `SKTypeface`, text measurements and run layouts, reused across frames |
| `SkiaFontRegistrar` | Registered and fallback font families, shared by every cache |
| `KumikoImageCache` | Bounded cache of decoded images for image cells, loaded through `IKumikoImageLoader` |
| `ICellRenderer` | Per-column-type cell content renderer (Text, Boolean, Image, ProgressBar, ActionButtons); receives a `CellRenderContext` |
| `KumikoColor` / `KumikoFont` / `KumikoPaint` / `KumikoRect` | Platform-independent value types |

### Hosts

| Class | Responsibility |
|-------|---------------|
| `KumikoDataGrid` (MAUI) | `ContentView` on an `SKGLView` or `SKCanvasView` (`RenderMode`); runs the platform frame loop, translates touch/scroll/keyboard events, owns the per-platform text input |
| `KumikoUIHostingExtensions` | `builder.UseKumikoUI()`: SkiaSharp, the canvas handler and font registration (MAUI only; Uno needs none), in `KumikoUIHostingExtensions.cs` |
| `KumikoDataGrid` (Uno) | `UserControl` on an `SKCanvasElement` or `SKXamlCanvas` (`RenderMode`); runs the `CompositionTarget.Rendering` frame loop, WinUI pointer events, a hidden `TextBox` for keyboard and input methods |
| `KumikoFonts` | Registers app fonts with `SkiaFontRegistrar` (MAUI and Uno each have one) |
| `KumikoFrameScheduler` | Platform-free frame loop state machine, in both hosts and unit-tested in both |

## Drawn Components

Every visual control inside the grid is custom-drawn on the SkiaSharp canvas: no native UIKit, AppKit, or WinUI controls are used. Seven are public; four are internal.

| Component | Purpose |
|-----------|---------|
| `DrawnTextBox` | Single-line text editor with caret, selection, undo, input-method composition (`ITextInputSession`) |
| `DrawnComboBox` | Filterable dropdown with keyboard navigation |
| `DrawnDatePicker` | Calendar popup with month navigation and optional time picker |
| `DrawnNumericUpDown` | [−] value [+] with auto-repeat and keyboard shortcuts |
| `DrawnScrollPicker` | Mobile-style scroll wheel with physics-based snapping |
| `DrawnFilterPopup` | Excel-style filter with search, checkboxes, and sort options |
| `DrawnActionButtons` | The buttons of an action button column |
| `DrawnCheckBox` (internal) | Three-state checkbox (checked/unchecked/indeterminate) |
| `DrawnProgressBar` (internal) | Read-only bar or interactive slider with drag thumb |
| `DrawnFocusManager` (internal) | Single focus holder with Tab cycling |
| `PopupManager` (internal) | Popup stack, z-order and input priority |

All derive from `DrawnComponent` (`Components/DrawnComponent.cs`), which defines the drawing, pointer, key, focus and animation hooks and the `ValueChanged` / `EditCompleted` signals.

## Architectural Patterns

### Zero Native Controls
Every UI element is drawn directly on the SkiaSharp canvas. This ensures pixel-perfect consistency across platforms and avoids the complexity of native control lifecycle management.

### Clean Rendering Abstraction
`IDrawingContext` isolates all drawing from SkiaSharp. Adding a new backend requires only implementing this interface and providing a host view.

### 3-Pass Frozen Column Rendering
Scrollable, left-frozen, and right-frozen columns are each rendered in separate clip regions with identical draw call sequences (`DrawPaneRows`, `DrawHeader`, `DrawSortIndicators`, `DrawFilterIcons`, `DrawFrozenRows`), in `KumikoRenderer.RenderFrame`. This maintains correct z-ordering while keeping the code DRY. `FrozenPanes.Resolve` unpins frozen columns that do not fit the viewport, and the layout engine, scroller, hit tester and input controller all read the resulting per-column pane.

### Zero-Allocation Frames
A steady-state frame allocates no managed memory: `PaintCache` rebuilds paints only on a style change, `KumikoSource` caches each drawn cell's display text, `KumikoLayoutEngine` has `Populate*` list variants, hit testing returns a value (`KumikoHitInfo`), drawn components memoize paints (`PaintMemo`, internal), and the SkiaSharp context is reused (`SkiaResourceCache.CreateContext`) over cached native objects, text measurements and text blobs. `RenderAllocationTests` (through a no-op context) and `SkiaAllocationTests` (through a real surface) assert 0 bytes, and `PerformanceBudgetTests` holds the timing budgets.

### Property Accessors
`KumikoAccessorRegistry` resolves a column's dotted property path (for example `"Address.City"`) to `KumikoPropertyAccessor` segments cached per `(type, path)`. A type marked `[KumikoGridItem]` gets generated, reflection-free accessors (`KumikoUI.SourceGenerators`); any other type gets accessors compiled from `Expression.Property` chains by `ReflectionAccessorFactory`, which Native AOT and trimming cannot rely on. A column can also set `ValueAccessor` and `ValueSetter` itself.

### Popup Input Priority System
`PopupManager` (owned by `KumikoInputController`) intercepts all input before the grid. A hit on a popup is consumed. A press outside a popup dismisses all popups but does **not** consume the event, so the grid still processes the click. `KumikoRenderer.RenderFrame` draws the popups last.

### Cascading Style Resolution
`KumikoCellStyle` has nullable properties with `Merge(primary, fallback)`. Resolution order:
1. Per-cell dynamic style (`KumikoStyle.CellStyleResolver`, with `RowStyleResolver` for rows)
2. Column `KumikoCellStyle`
3. Grid defaults from `KumikoStyle`

On the hosts, explicit style properties (`RowHeight`, `ShowHorizontalGridLines`, ...) are held in `KumikoStyleOptions` and re-applied over whatever theme or style is current, and `FollowSystemTheme` picks the theme from the app.

### O(1) Incremental Updates
`KumikoSource.TryIncrementalUpdate` handles simple `INotifyCollectionChanged` Add/Remove operations without a full rebuild (`RebuildCore`) when no sort, filter, group, or summary transforms are active.

A `PropertyChanged` of a property that only table summaries use rebuilds nothing (#69): Sum, Average and Count keep each visible row's value and apply the change in O(1); Min, Max and Custom are recomputed over the visible rows without re-filtering, re-sorting or regrouping. Inside `BeginUpdate`, a collection change that needs a rebuild only marks the view stale, so a batch rebuilds once (when the returned `KumikoUpdateScope` is disposed, or at the first row read).

### Background View Rebuilds
From `KumikoSource.BackgroundRebuildThreshold` items (hosts set `KumikoSource.DefaultBackgroundRebuildThreshold`, 10,000; a source you create stays synchronous), a rebuild for a sort, filter, grouping or summary change runs on a worker (`KumikoSource.Background.cs`, `ViewBuilder`). It works from a snapshot of the items and the settings, and produces a `ViewSnapshot` (the visible rows, group structure and summaries). The finished snapshot is swapped in on the source's thread through its captured `SynchronizationContext`, raising `ViewChanged` (`KumikoViewChangeKind.Rebuild`) and then `ViewUpdated`. Until then every read answers from the current view, so reads never block and never see a half-built view; selection and the current cell are tracked by item, so they follow into the new order. Requests made in one turn of the UI thread start one build, a newer request cancels a running one, and after two cancellations in a row a running build is allowed to finish. `IsViewUpdatePending` and `WhenViewUpdatedAsync` expose the state. Delegates that run on the worker (accessors, comparers, predicates, key and aggregate selectors) must only read.

### Thread affinity
A `KumikoSource` belongs to the thread that called `SetItems` or `Attach` (the UI thread). Collection changes, item `PropertyChanged` and calls from any other thread throw `InvalidOperationException` before the view is touched; the source then resyncs on its own thread through the captured `SynchronizationContext` (or on the next `Refresh`). The view is therefore only ever read and written on the UI thread (or by a background build from its own snapshot), and the hosts repaint from `ViewChanged` and `ViewUpdated`.

### Physics-Based Scrolling
`InertialScroller` tracks velocity with an exponential moving average and decays it by `ScrollSettings.Friction` per 16 ms, integrated over the measured frame interval, so a fling travels the same distance at 60 and 120 Hz. `KumikoMomentumPreset` (Default, Ios, Android, Desktop) picks the feel per platform.

### Platform Keyboard Convergence
The platform input mechanisms converge on the same Core types: command keys become `KumikoKeyEventArgs` → `KumikoInputController.HandleKey`, and text and input-method composition go to the open editor's `ITextInputSession`:
- **iOS/Mac Catalyst (MAUI)**: `KeyInputResponder` (UIView with `UIKeyCommand` + `UITextInput`): text and composition go through `AppleTextInputBridge`; navigation keys go to `HandleKey`
- **Android (MAUI)**: `KumikoTextInputView` with a `KumikoInputConnection` over `AndroidTextInputMapper`; hardware keys go to `HandleKey`
- **Windows (MAUI)**: the grid's platform view: WinUI `PreviewKeyDown`/`CharacterReceived` through `WindowsKeyInput`, and a `CoreTextEditContext` adapter (`TextEditContextState`) for the open text editor
- **Uno, every head**: a hidden `TextBox` mirrors the editor's text; `KumikoTextInputAdapter` replays its `TextChanging` and composition events on the `ITextInputSession`, and its `KeyDown` sends command keys to `HandleKey` (`InputMapping` maps `VirtualKey` to `KumikoKey`)

Core's `KumikoKeyboardAvoidance` computes how much of the grid an on-screen keyboard covers; both hosts feed it and set `ScrollState.BottomInset`.

### Virtual Scrolling
Only visible rows and columns are computed and drawn. `KumikoLayoutEngine.GetVisibleRowRangeWithOffset` gives the row range from the scroll offset, row height, header, summaries and frozen rows; the `PopulateVisible*` methods give the column ranges per pane.

### Grouped Flat View
Hierarchical group data is flattened into the view's list of `FlatViewRow`, with `FlatRowKind` (Data, GroupHeader, GroupSummary). Group paths are `GroupKeyPath` composite keys. Expansion state is tracked per group; `PinnedGroupHeaders` computes the sticky headers for the scroll offset.

### HitTest Region System
13 `HitRegion` values (None, Cell, HeaderCell, HeaderResizeGrip, HeaderFilterIcon, RowDragHandle, EmptyArea, GroupHeaderRow, GroupChevron, GroupPanelChip, GroupPanelChipRemove, GroupSummaryRow, TableSummaryRow) are resolved across the three column panes by `KumikoHitTester.HitTest`. The public overload returns a `KumikoHitTestResult`; `HitTestCore` returns the allocation-free `KumikoHitInfo` used on every hover move. Target sizes widen for a finger (`KumikoPointerDeviceType.Touch`), and frozen panes, frozen rows, sticky group headers and the pinned footer are resolved as the renderer draws them.

### Host Surfaces and the Frame Loop
Both hosts draw into a private `KumikoSurface` / `IKumikoSurface` chosen from `RenderMode`, coalesce every redraw request through `KumikoFrameScheduler` and run a platform frame callback (`CADisplayLink`, `Choreographer`, `CompositionTarget.Rendering`) only while a fling, an autoscroll, an editor animation or a deferred redraw needs it. See [RENDERING.md](RENDERING.md#surfaces-and-frame-loop).
